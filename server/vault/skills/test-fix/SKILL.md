# test-fix

## 核心目标与边界

以失败证据为起点，诊断并修复测试或实现缺陷：

- **做**：从失败信号出发 → 缩小范围 → 定位根因 → 修复 → 验证修复
- **不做**：在无失败证据时做预防性修改；大批量重构（那是 coding 的职责）；修改测试让它"变绿"而不修复真实问题

## Hard Gates

- `real_failure_signal_present`：必须有真实失败信号（测试日志、报错输出、CI 失败记录）
- `required_input`（failure_log）：失败日志不得为空

没有真实失败信号 = 拒绝启动。这是核心安全约束，防止猜测式修复。

## 主流程

1. **信号分析** — 从失败日志中提取：错误类型、发生位置、相关输入、是否可复现
2. **范围缩小** — 二分法定位：是哪次变更引入的？哪个模块出问题？
3. **根因诊断** — 利用 KB 和代码上下文判断根因类型：逻辑错误 / 测试数据问题 / 环境差异 / 竞态 / 边界未处理
4. **修复方案** — 给出最小修复方案（只改必要的代码），避免连带改动
5. **验证** — 修复后重新执行失败的测试，确认 pass
6. **沉淀** — 如果根因具有可复用经验，建议 deposit-answer 沉淀

## 关键决策点

- 根因不在代码而在测试本身时（测试写错了）：修复测试，但需标注"测试修正"而非"bug 修复"
- 根因需要跨模块修复时：记录所有受影响模块，按依赖顺序修复
- 修复涉及方案变更时：不直接修改方案，返回 coding 或 tech-solution 处理

## 需要读取的资源

- `references/`：常见错误模式（error-patterns），诊断决策树（diagnostic-tree）

## 输出规格与验证

- 输出：修复的代码 + 诊断记录（保存到 `runs/<run_id>/test-fix-log.md`）
- 验证：失败测试变为 pass；修复不引入新的测试失败；诊断记录包含根因和证据链
