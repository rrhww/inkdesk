# architecture-patterns

tech-solution 生成技术方案时可参照的架构决策模式。这些模式是启发式规则，不是强制约束。

## 模式索引

### AP-01: 最小接口优先
当有选择时，优先定义最小外部接口——只暴露调用方需要的，不暴露内部状态。
- 适用：新模块设计
- 反模式：把所有内部方法都设为 public

### AP-02: 显式数据流
数据从哪来、经过哪些组件、最终落到哪——每一步必须在方案中可追溯。
- 适用：涉及数据存储或消息传递的方案
- 反模式：用「系统处理」掩盖数据路径

### AP-03: 单一写入者
对同一数据存储，只有一条写入路径。多个模块需要写入时通过单一写入者接口。
- 适用：wiki 内容更新、数据库写入
- 反模式：多个模块各自直接写同一数据源

### AP-04: 独立可验证
每个模块应能独立于其他模块验证其功能——如果不能，边界需要调整。
- 适用：模块拆分决策
- 反模式：模块 A 只有在模块 B 运行时才能测试

### AP-05: 配置外部化
可变参数（阈值、路径、超时）应外部化为配置，不硬编码在逻辑中。
- 适用：任何有可变参数的方案
- 反模式：`MAX_RETRY = 3` 直接写在模块代码里

## 决策记录格式

方案中每个关键架构决策应记录：

```
**决策**: [选了什么]
**备选**: [考虑过但没选的方案]
**理由**: [为什么选这个]
**代价**: [选这个带来的限制]
```

## 不做

- 不要求方案穷举所有模式——只列出相关决策
- 不把模式当作硬性约束（具体场景可偏离）
