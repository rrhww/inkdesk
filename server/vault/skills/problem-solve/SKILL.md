# problem-solve

## 核心目标与边界

以异常现象为起点，利用所有可用信息源做系统性诊断：

- **做**：收集信号 → 缩小范围 → 定位根因 → 产出诊断报告和修复建议
- **不做**：直接修改代码（修复由 coding 或 test-fix 执行）；在无任何信号时做猜测

## Hard Gates

- `required_input`（symptom_description）：现象描述不得为空
- `vault_initialized`：KB 未初始化时提示但允许继续（排查可能需要代码仓信息而非 wiki）

## 主流程

1. **信号收集** — 现象描述 + 报错信息 + 近期变更记录 + 相关日志
2. **范围判断** — 区分：代码 bug / 配置错误 / 环境问题 / 依赖变更 / 数据异常
3. **近期变更关联** — 检查近期的代码变更、依赖升级、配置修改与现象的时间关联
4. **根因诊断** — 利用 KB 中的已知问题和架构知识，形成根因假设并验证
5. **修复建议** — 给出最小可验证的修复步骤和验证方法
6. **复盘文档** — 产出现象→诊断→根因→修复→预防的完整复盘

## 关键决策点

- 根因无法唯一确认时：列出所有可能原因和各自的验证方法，按可能性和验证成本排序
- 问题可被 test-fix 快速处理时：建议将修复委托给 test-fix，本 Skill 只做诊断
- 发现系统性缺陷时：完整记录，建议纳入架构 review

## 需要读取的资源

- `references/`：诊断决策树（diagnostic-tree），已知问题库（known-issues）

## 输出规格与验证

- 输出：诊断报告（保存到 `runs/<run_id>/diagnosis.md`）
- 验证：报告包含完整证据链（现象 → 排查步骤 → 根因 → 修复建议）；每个排查步骤有发现；修复建议可执行
- 复盘文档包含预防措施

## 下游衔接

- → [coding] 或 [test-fix]：修复执行
- → [deposit-answer]：根因和解决方案沉淀为 wiki 知识
