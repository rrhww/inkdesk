# diagnostic-tree

诊断决策树——problem-solve 的核心诊断路径。此树与 test-fix 的 diagnostic-tree 共享结构但聚焦线上/环境异常。

> 注：本文件与 test-fix 的 references/diagnostic-tree.md 内容结构相同但侧重不同。problem-solve 侧重系统性排查，包括近期变更关联、环境差异和根因假设验证。

## problem-solve 诊断树

```
异常现象
  │
  ├─ 信号收集
  │    ├─ 现象描述 + 时间线
  │    ├─ 报错/异常信息 + 堆栈
  │    ├─ 近期变更记录（commit / deploy / config change / dependency upgrade）
  │    └─ 相关日志（应用日志 + 系统日志 + 依赖服务日志）
  │
  ├─ 范围判断
  │    ├─ 代码 bug —— 逻辑错误、边界未处理、异常路径触发
  │    ├─ 配置错误 —— 环境变量、连接字符串、特性开关
  │    ├─ 环境问题 —— 依赖缺失、版本不兼容、资源不足（内存/磁盘/连接池）
  │    ├─ 依赖变更 —— 上游 API 不兼容、库升级行为变化、第三方服务异常
  │    └─ 数据异常 —— 脏数据、schema 不匹配、迁移遗漏、编码问题
  │
  ├─ 近期变更关联（核心诊断手段）
  │    ├─ 最近 24h/7d 内有代码变更？→ git log --since
  │    ├─ 最近有依赖升级？→ dependency changelog diff
  │    ├─ 最近有配置修改？→ config diff
  │    └─ 变更时间与现象出现时间是否吻合？
  │         └─ 吻合 → 该变更是第一嫌疑人
  │
  ├─ 根因假设形成
  │    ├─ 列出所有可能原因（按可能性和验证成本排序）
  │    ├─ 每个假设：如果为真，应能观察到什么？
  │    └─ 验证：优先做成本最低的验证
  │
  └─ 根因确认
       ├─ 可通过代码证据或日志证据唯一确定？→ 确认
       ├─ 无法唯一确定？→ 列出所有可能原因，标记各自的置信度
       └─ 需要环境外信息（如生产权限、第三方确认）？→ 标记为待确认
```

## 终止条件

- 根因唯一确定，有完整的「现象 → 排查步骤 → 根因」证据链
- 所有可验证路径均已排除，剩余可能原因需要外部信息

## 不做

- 不在第一步就跳到结论
- 不在无信号时做猜测
- 不修改代码（诊断与修复分离）
