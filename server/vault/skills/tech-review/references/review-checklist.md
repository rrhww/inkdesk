# review-checklist

tech-review 的结构化检查项。每项检查必须带 evidence——不能是 reviewer 的主观判断。

## 检查清单

### D1: 边界
- **检查**：方案是否明确声明了「做什么」和「不做什么」？
- **通过标准**：方案中有显式的「范围」或「边界」章节，清晰列出 excluded scope
- **Evidence 要求**：引用方案中的具体段落
- **阻塞级别**：缺少 → BLOCKED

### D2: 风险
- **检查**：方案是否识别了关键风险并给出了缓解措施？
- **通过标准**：每个标为高/中的风险都有对应的缓解措施
- **Evidence 要求**：列出每个风险和其缓解措施的对应关系
- **阻塞级别**：2 个以上高风险无缓解 → BLOCKED

### D3: 依赖
- **检查**：外部依赖（库、服务、数据库、API）是否显式声明了版本和风险？
- **通过标准**：每个外部依赖都有名称和版本约束
- **Evidence 要求**：列出所有声明的外部依赖
- **阻塞级别**：缺少关键依赖声明 → BLOCKED

### D4: 接口
- **检查**：对外接口的输入/输出/错误是否足够精确？
- **通过标准**：关键接口有类型和约束描述；错误路径被考虑
- **Evidence 要求**：引用方案中接口定义的段落
- **阻塞级别**：接口完全未定义 → BLOCKED；部分模糊 → NEEDS_FIX

### D5: 数据流
- **检查**：数据路径是否可从头到尾追踪？
- **通过标准**：可以从输入追踪到每个中间步骤直到最终存储/输出
- **Evidence 要求**：描述完整的数据流路径
- **阻塞级别**：数据流不可追踪 → NEEDS_FIX

### D6: 测试覆盖
- **检查**：方案是否给出了测试范围和关键验收点？
- **通过标准**：至少包含单元测试 + 集成测试范围的描述；验收点可测量
- **Evidence 要求**：引用方案中测试部分的具体内容
- **阻塞级别**：完全无测试描述 → NEEDS_FIX

## Review 结果分类

- **PASSED**：所有 BLOCKED 项均通过，NEEDS_FIX 项 ≤ 2 且不严重
- **NEEDS_FIX**：存在 BLOCKED 项或 >2 个 NEEDS_FIX 项
- **SKIPPED**：方案过于简略，无法评审（需补充后重新提交）

## 不做

- 不判断方案是否符合业务需求（human review 的职责）
- 不生成替代方案（修改方案是 tech-solution 的职责）
- 不要求方案完美——只要求关键信息不缺失
