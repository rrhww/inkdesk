# 4.2.1 Dry-Run Review — 13 Skill 深度审查

> 审查方式：逐 SKILL.md 对照 contract.json，沿五个维度检查：
> Hard Gates 可判定性、主流程完整性、边界清晰度、验证标准可执行性、上下游衔接一致性。
> Runtime 不存在，所有问题标记为待实战验证。

## 总体评价

13 个 Skill 的结构设计**在原则层面是正确的**。producer/reviewer/diagnostic 三种 Kind 的写作风格区分清晰：
- producer 给模型发挥空间（如 ingest-source、coding）
- reviewer 保留结构化检查项 + evidence（tech-review）
- diagnostic 从真实信号出发，禁止猜测（test-fix、problem-solve）

但 dry-run 暴露了两类问题：
- **数据质量问题**：contract.json 与 SKILL.md 不一致、重复字段
- **空资源目录**：所有 references/ 和 templates/ 都是空的

## 系统性问题

### 1. 空资源目录（影响面 8/13）

以下 Skill 的 SKILL.md 声明了需要读取的资源，但对应目录为空文件：

| Skill | 声明的资源 | 缺失文件 |
|-------|-----------|---------|
| ingest-source | `references/entity-extraction-rules`, `references/proposal-template` | 2 个 |
| answer-from-wiki | `references/search-strategy`, `references/confidence-rules` | 2 个 |
| run-wiki-health | `references/health-check-items`, `references/scoring-formula` | 2 个 |
| skill-router | `references/routing-tree`, `references/domain-skills-summary` | 2 个 |
| tech-solution | `references/architecture-patterns`, `templates/solution-template.md` | 2 个 |
| tech-review | `references/review-checklist` | 1 个 |
| coding | `references/coding-standards`, `references/architecture-constraints` | 2 个 |
| test-prep | `templates/test-plan-template.md` | 1 个 |
| test-fix | `references/error-patterns`, `references/diagnostic-tree` | 2 个 |
| problem-solve | `references/diagnostic-tree`, `references/known-issues` | 2 个 |

这些文件是 Skill 执行时的"领域知识补充"——在没有 Runtime 的阶段，它们为空是**结构上合法但内容上不完整**。实战时模型会因找不到指定文件而用自身知识填充，**丧失 Skill 设计意图中对特定资源文件的依赖**。

### 2. SKILL.md ↔ contract.json 一致性缺陷（影响面 2/13）

- **tech-solution**: `schema_gate_passed` 在 SKILL.md 中声明为 Hard Gate，contract.json 缺失
- **problem-solve**: `vault_initialized` 在 SKILL.md 中声明为 Hard Gate，contract.json 缺失
- **patch-wiki-page**: contract.json 中 `required_input` 重复（功能上无害但数据不整）

### 3. Hard Gate 的 "block vs warn" 语义未建模

当前 contract schema 的 `hardGates` 是一个 gate-kind 的列表。但多个 Skill 存在"软门禁"：
- `ingest-source`: schema_gate_passed → block（阻止）
- `run-wiki-health`: schema_gate_passed → warn（提示但继续）
- `problem-solve`: vault_initialized → warn（提示但继续）
- `tech-solution`: schema_gate_passed → warn（提示但继续）

相同 gate-kind 的阻塞语义不同，但 contract.json 不区分。这在 Runtime 执行时会导致不一致——是 block 还是 warn 需要看 SKILL.md 的 human-readable 描述，机器只能读到 gate-kind。

**建议**：将 gate 建模为 `{kind: string, severity: "block" | "warn"}` 以区分硬阻塞和软提醒。但这属于 SDK 变更，需评估影响。

### 4. human_confirmation gate 未在 SDK 注册

`coding` 的 contract.json 中有 `human_confirmation` gate，但这是一个非标准的 gate-kind。当前 validator 不认识它也会放行（gate-kinds 没有被枚举限制）。这导致其他 Skill 也使用它时没有契约保证，且未来无法做一致性 lint。
