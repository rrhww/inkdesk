Focus episode · 方案设计

为什么评分和门禁必须分离？如何设计不可绕过的 Gate？

回到当时：你已经知道什么

  • 健康系统需要给用户一个整体评分（质量感）
  • 同时需要一个硬性门禁来阻止低质量提交进入下一步环节
  • 8 条规则分三个严重度：error / warning / info
  • error 表示结构缺陷（非法状态、重复标题、来源丢失），warning 表示需要注意但可继续
  • Evaluation Run 是正式评测环节，不应在数据有严重问题时启动
  • 评分的含义是'整体健康程度'，门禁的含义是'是否可以进入下一阶段'

场景倒带

现在要设计这个健康系统。前端需要显示一个 0-100 的分数，后端需要一个布尔值来阻止 Eval Run 的创建。你会把这两个信号设为一个（分数低于某个阈值就阻塞），还是分开？如果是分开的，门禁的规则应该是什么？

  • 思考：如果一个页面只有 warning 和 info 级别的发现，评分可能是 70%，但应该被阻止吗？
  • 思考：如果一个库有 100 个页面，只其中 1 个页面的状态非法（error），评分可能很高（99%），这个库可以进入 Eval Run 吗？
  • 思考：未来如果需要新增规则类型，门禁逻辑需要改动吗？哪种设计更容易扩展？

会话证据

定义评分公式：passed_applicable / total_applicable × 100

每个规则对其适用的页面检查一次。评分计算所有规则×适用页面的通过率，与 severity 无关。一个 KB_INVALID_STATUS(error) 和一个 KB_SHORT_PAGE(warning) 对分数的贡献相同——都是'不通过'。

这一步改变了什么： 分数反映的是'有多少检查通过了'，不区分严重度。这是合理的——分数是对现状的总体描述。

会话证据

定义门禁规则：存在任意 error 级别的发现 → Gate FAILED

在 health_service.py 中，扫描完成后遍历所有发现。只要 findings 列表中出现 severity=='error' 的项，gateStatus 就设为 FAILED；否则 PASSED。分数为 null（无适用检查）时 Gate 仍可评估。

这一步改变了什么： 门禁是一个简单、清晰的规则：error 出现 = 阻塞。不依赖分数阈值，不依赖总数，不依赖比例。这就是分离的关键价值。

会话证据

在 Evaluation Service 中前置 Gate 检查

create_eval_run 方法第一步就检查传入的 gate 状态。如果 gate 不是 PASSED，直接抛出 ValueError，在 FastAPI 路由中被捕获为 HTTP 409（EVAL_RUN_REJECTED）。这意味着 Eval Run 的创建路径上有一个不可绕过的检查点。

这一步改变了什么： 门禁不是隐式约定，而是代码路径上的硬断言。即使前端跳过检查直接调 API，后端也不允许创建。

改进建议

如果重新设计，考虑将 gate 规则表显式化

当前 gate 逻辑硬编码为 '存在 error = FAILED'。未来如果有更复杂的 Gate 规则（例如 3 个以上 warning 也算 FAILED），可以考虑将 Gate 的计算从 '遍历 findings 判断 severity' 抽离为一个独立的 gate_policy(): bool 函数，接受整个扫描结果，返回 PASSED/FAILED。

这一步改变了什么： 使门禁策略独立于健康扫描和评分计算，三者各管各的，改变任何一个不影响其余。

Mental model

带走这个底层模型

描述性指标 ≠ 决策性信号

健康评分描述系统的整体状态（0-100 分），门禁回答一个二分问题（现在能推进吗？）。混淆二者会导致：阈值调整影响评分可读性，评分波动导致门禁不稳定，新增规则类型需要重新校准阈值。分离之后各自独立演化。

门禁规则应尽量简单，越复杂的门禁越难解释

'存在 error = FAILED' 这条规则有两个优点：（1）任何人都能理解为什么被阻止；（2）增加新规则时，只需决定新规则的 severity 是什么，不需要修改门禁逻辑。severity 是规则的属性，门禁只看 severity，规则本身是什么不重要。

安全关键路径上的检查必须在服务端不可绕过

Eval Run 的创建必须检查 Gate，这个检查在服务端方法体内执行，不是中间件、不是前端判断。即使 API 被直接 curl 调用，也无法绕过。'不可绕过'不等于'隐藏'——错误信息通过 HTTP 409 明确返回，告诉调用者需要修复什么。

Near transfer

换一个场景，再做一次判断

你正在为一个 CI 流水线设计质量门禁。流水线有 5 个步骤：lint、typecheck、unit test、e2e test、bundle size check。每个步骤的结果有 pass/warn/fail。你需要在流水线末尾加一个 '部署审批' 节点来决定是否允许部署。请设计这个审批节点的规则：你会用加权总分还是硬性条件？哪些步骤的 fail 应该阻塞部署？哪些 warn 累积到一定量也应该阻塞？

  • 哪些步骤失败应该无条件阻塞部署？为什么？
  • lint warning 和 typecheck fail 的严重度可能不同——你如何定义这个差异？
  • 如果未来新增一个 'secret scan' 步骤，你的阻塞规则需要改动吗？如果不改动，原因是什么？
作答后展开参考思路

推荐方案：每个步骤定义自己的严重度（fail = error 级，warn = warning 级）。部署审批的规则是：存在任意 error 级结果 → 阻塞。这个规则不关心步骤总数、不关心分数、不关心 warning 数量。原因：（1）添加新步骤时只需定义该步骤的 fail 含义，不修改审批逻辑；（2）warning 提供信息但不阻塞——lint warning 不应该阻止热修复部署；（3）如果需要 '3 个 warning = 阻塞' 的规则，把它写成一个独立的步骤（如 '聚合检查'），而不是嵌入每个步骤。

Reusable checklist

下次可以直接使用

  • 设计质量门禁前，先区分：哪些是指标（descriptive），哪些是决策（prescriptive）
  • 门禁规则用 severity 而非具体类型——新增规则时不需修改门禁
  • 阻塞检查放在服务端代码路径上，不可仅依赖前端判断
  • 阻塞时返回明确的 HTTP 状态码和解释信息，告诉用户需要修复什么
  • 评分公式保持独立，只有描述性含义，与阻塞决策解耦
