# 领域模型

## 目标

统一 Inkdesk 知识优先、需求驱动的业务语言。当前主路径是：

```text
Source -> Topic / Claim -> Briefing / Health
      -> Task Context Assembly -> Execution / Review
      -> Knowledge Deposit Proposal
```

知识层表达长期理解，任务层表达研发执行，二者通过 Context Pack、Knowledge Signal 和引用关系连接，但不共享状态含义。

## 核心角色

### Owner

当前唯一主要用户，负责浏览和维护知识、创建实时需求、审阅认知变更、确认任务 Review 和正式完成。

### ExternalAgent

未来通过 MCP、CLI、Skill 或 Codex 接入。可以请求 Context Pack、报告执行发现和提交知识沉淀提案，但不能直接写正式知识或批准完成。

## 知识实体

### Workspace

单 owner 的逻辑边界，承载 source、topic、task、review 和执行记录。

### Source

`raw/` 中可追溯的原始材料，如网页、PDF、PRD、ADR、代码说明和历史方案。必须保留来源定位和更新时间，可被多个主题引用。

### Topic

知识看板的第一产品对象，对应一个模块、业务概念、技术主题或历史决策。包含 summary、current understanding、open questions、health signals 和关联关系。

### TopicClaim

主题中的稳定判断。每条 claim 应说明状态、适用范围、更新时间，并尽量绑定一个或多个 Evidence。

### Evidence

支持或反驳 claim 的来源定位。Evidence 指向 Source 的具体片段、代码路径、提交或验证结果，不等于模型生成的解释。

### KnowledgeSignal

由知识健康或研究过程产生的可行动信号，包括 `missing_evidence`、`conflict`、`stale`、`open_question`、`decision_gap`。信号可以创建任务，但不能直接改变 Topic 状态。

### ReviewItem

等待人工裁决的知识提案，包括新建主题、patch、补证、冲突处理和开放问题。未接受前不能写入正式 wiki。

### AskTurn

一次知识搜索或 Context Ask 及其引用快照。记录问题、回答、来源、知识缺口和可选 deposit proposal。

## 任务与上下文实体

### Task

研发任务对象，来源不限定为知识：

```text
originType:
  realtime_requirement
  knowledge_signal
  execution_finding
  manual
```

`originRef` 可选地指向 PRD/Bug、KnowledgeSignal、ExecutionEvent 或外部引用。任务状态表达执行进度：`backlog`、`ready`、`doing`、`review`、`blocked`、`done`。

一个 Task 可以关联多个 Topic、Claim、Evidence 和 Source；一个 Topic 也可以支撑多个 Task。任务状态变化不得改变知识状态。

### ContextPack

为任务或 Agent 执行装配的上下文快照，包含任务目标、相关主题、关键 claim、证据定位、代码路径、约束、风险和未解问题。ContextPack 必须可追溯生成时间和引用来源。

### KnowledgeGap

任务检索后未找到足够知识时的明确记录，描述缺少什么、影响哪个判断、建议如何补证。KnowledgeGap 不阻塞任务创建，但在进入执行前必须与任务一起保存。

### ContextAssembly

任务创建后的上下文装配过程，状态固定为：

```text
pending -> searching -> ready | gap | failed
```

只有 `ready` 或 `gap` 的任务可以进入 `ready`/`doing` 执行阶段。`failed` 必须可重试或由用户处理。

### ExecutionFinding

执行或验证过程中发现的新风险、测试失败、回归、后续优化或未完成事项。可作为新的 Task 来源，也可提交知识沉淀提案。

### DevRun

任务执行的阶段性运行记录。它是 K4 任务看板和 K5 Codex 执行阶段的派生执行对象，不是当前 K1 知识看板的主入口。DevRun 记录 ContextPack、attempt、事件、artifact、review 和完成决定。

### ExecutionAttempt / ExecutionEvent

一次具体 Agent 或本地执行尝试及其可见事件。允许中断和恢复，不能保存隐藏推理、秘密或完整环境变量。

## 沉淀实体

### DepositRequest

来自 Ask、Task 或 ExternalAgent 的知识沉淀请求。输入包括回答或产物、选择片段、引用、任务和执行上下文。输出是 ReviewItem，不是直接写入 Topic。

### DepositTrace

沉淀流水线的可审计痕迹，包括提取、证据绑定、主题路由、冲突检查、patch 生成和质量门禁结果。

## 派生视图

- Topic Knowledge Board：主题卡、筛选、健康和最近变化；
- Topic Briefing：主题摘要、claim、evidence、source、代码和问题；
- Graph Explorer：关系探索辅助视图；
- Task Board：多来源研发任务执行视图；
- Context Pack View：任务执行前的上下文快照；
- Review Queue：知识提案和任务 Review；
- Health View：知识信号和复核入口。

## 关系约束

```text
Source -> Evidence -> TopicClaim -> Topic
Topic / KnowledgeSignal / Requirement / Finding / Manual -> Task
Task -> ContextAssembly -> ContextPack | KnowledgeGap
Task -> ExecutionAttempt -> ExecutionFinding
Task / AskTurn / ExecutionFinding -> DepositRequest -> ReviewItem -> Topic
```

- 知识和任务是多对多关系；
- 实时需求可以没有现有知识直接建卡；
- 没有知识必须转化为 KnowledgeGap，而不是被忽略；
- Context Pack 是执行门禁，不是建卡门禁；
- AI 只能提出知识变更，Owner 才能接受正式写入和最终完成；
- Codex/CDP 适配层不持有上述业务真相。

## 边界说明

- 当前没有访客、团队协作或公开阅读面；
- `/app/wiki` 是当前产品主入口，`/app/runs` 在后续阶段承接任务看板；
- 图谱不替代主题内容；
- Vault Markdown 是长期真相，数据库和 UI 都必须可从它恢复；
- 外部 Agent 通过 context/deposit 协议接入，不直接写长期知识；
- 不恢复旧的 plans、public 或通用 issue tracker 主路径。
