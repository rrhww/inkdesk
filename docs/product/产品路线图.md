# Inkdesk 产品路线图

## 目标

Inkdesk 按“知识内容先成熟、需求执行后扩展”的顺序演进：

```text
K0 产品与知识模型校正
  -> K1 主题知识看板
  -> K2 证据与知识健康
  -> K3 多来源研发需求与上下文装配
  -> K4 dashi 式研发任务看板
  -> K5 Codex 执行与宿主接入
```

知识信号是研发任务的一种来源，实时 PRD、Bug、重构、临时改造和执行发现预计会成为更高频来源。Context Pack 是执行门禁，不是建卡门禁。

## K0：产品与知识模型校正

### 目标

- 将产品叙事从 `Dev Run-first` 改为 `Knowledge Context-first`；
- 将 `/app/wiki` 定义为当前主入口；
- 将关系图定位为辅助探索视图；
- 统一 Topic、Claim、Evidence、Knowledge Signal、Task 和 Context Pack 的边界；
- 将 dashi 和 Codex 相关能力移到 K4-K5。

### 完成标志

- 产品愿景、定位、MVP、领域模型和长期路线图语义一致；
- 不再声明所有任务都由知识对象产生；
- 不恢复或批量还原已删除的旧模块。

## K1：主题知识看板

### 目标

让用户围绕真实研发问题获得可读、可信、可追溯的主题上下文。

### 核心能力

- 主题卡：摘要、决策、文档、代码路径、来源数量、更新时间、未解问题和基础健康信号；
- 主题搜索：支持模块、业务概念、历史决策和研发问题；
- 主题简报：当前理解、关键决策、来源、代码、关联主题、不确定性；
- 来源追溯：从结论回到文档原文；
- 图谱辅助：从主题详情进入关系探索；
- 文件变化后的派生索引刷新；
- 只读知识 API 和 SSE 失效提示。

### 完成标志

- 三类真实查询能生成带来源的主题简报；
- 无来源内容不会被表达为确定事实；
- 列表、详情、原文和关系图可互相跳转；
- 独立 Web 的关键路径通过浏览器验收。

## K2：证据与知识健康

### 目标

让用户知道哪些知识仍值得相信，并能从健康信号定位到具体内容。

### 核心能力

- Claim 与 Evidence 引用；
- stale、unsupported、conflicting、open question；
- 知识健康筛选和主题级汇总；
- 补证、冲突处理和更新提案；
- Review-first 写入边界。

### 完成标志

- 每类健康信号有固定测试数据和定位路径；
- AI 生成的变更未经审阅不能进入正式知识；
- 健康状态只表达知识可信度，不混用任务状态。

## K3：多来源研发需求与上下文装配

### 目标

承接真实研发需求，并在进入执行前为任务形成可验证上下文。

### 任务来源

```text
realtime_requirement  PRD / Bug / 重构 / 临时改造
knowledge_signal      缺证 / 冲突 / 过期 / 未解问题 / 决策缺口
execution_finding     风险 / 测试失败 / 回归 / 后续工作
manual                用户直接创建
```

实时需求可以立即进入 `Backlog`，不要求预先关联知识。

### 上下文装配

```text
任务
  -> 搜索主题、决策、文档和代码
  -> 生成 Context Pack
  -> 关联已有知识
  -> 或记录 Knowledge Gap
```

上下文状态固定为 `pending / searching / ready / gap / failed`。只有 `ready` 或 `gap` 可以进入 `Ready` 和 `Doing`。

### 完成标志

- 四类来源都能创建任务；
- 无知识关联不阻塞建卡；
- 每次执行前保存 Context Pack 或明确 Knowledge Gap；
- 知识信号任务可以回链到主题、Claim、Evidence 和原文；
- Knowledge Gap 可以继续转为补证事项。

## K4：dashi 式研发任务看板

### 目标

在多来源建卡和上下文装配稳定后，建设高密度研发执行工作面。

### 状态与交互

```text
Backlog -> Ready -> Doing -> Review -> Done
                       \-> Blocked
```

- 密集任务卡、筛选、排序和详情；
- 来源类型、上下文状态、优先级、风险、负责人和下一步动作；
- 受控拖拽和非法转换拦截；
- 知识、需求、代码、证据和执行记录互链；
- Review 与人工完成门禁。

### 完成标志

- 不同来源任务在同一看板管理；
- 卡片能够解释来源、上下文、风险和下一步；
- 任务状态变化不会修改知识真相；
- 任务看板保持研发专用，不扩展成通用项目管理器。

## K5：Codex 执行与宿主接入

### 目标

将已经稳定的知识与任务闭环带入 Codex，并让 Codex 使用经过装配的上下文执行任务。

### 核心能力

- 独立 Web 继续作为完整降级入口；
- Codex 全工作区 Host Adapter；
- 会话、仓库、分支和 worktree 绑定；
- `codex exec --json`、attempt、事件、resume 和 interrupt；
- 执行前注入 Context Pack；
- 执行结果进入 Review，并产生知识回写提案；
- CDP 仅负责宿主，不持有业务状态。

### 完成标志

- Codex 获得的任务上下文可追溯；
- 执行结果可回到任务、需求、知识和证据；
- Codex 嵌入失败时独立 Web 和数据不受影响；
- 正式知识写入和最终完成仍由人工门禁控制。

## 后续阶段

在 K5 之后，再以真实负载决定是否建设：

- Evaluation 与 Capability Registry；
- 固定 Playbook 和受控 Harness；
- 团队协作与云控制面；
- 多执行器、Replay 和 Outcome 反馈。

没有真实任务和评测证据时，不建设通用工作流画布、高自治调度或自动 Capability Promotion。

## 跨阶段指标

| 维度 | 主要指标 |
| --- | --- |
| 知识可用性 | 主题简报命中率、来源覆盖率、无依据内容比例、检索到有效上下文时间 |
| 知识健康 | stale/unsupported/conflicting 定位率、复核完成率、误报率 |
| 上下文 | Context Pack 就绪率、Knowledge Gap 明确率、执行前上下文失败率 |
| 任务 | 实时需求建卡时间、状态阻塞原因可见率、Review 返工次数 |
| 执行 | 事件完整率、恢复率、Context Pack 使用率、人工门禁覆盖率 |
| 安全 | 静默知识写入次数、Secret/隐藏推理泄露、越权动作次数 |

## 顺序约束

- K1 未形成真实可用主题简报，不启动任务看板 UI 扩张；
- K2 未建立证据和复核边界，不让 Agent 自动回写正式知识；
- K3 未稳定 Context Pack/Knowledge Gap，不让任务进入自动执行；
- K4 未证明高频任务路径，不把 CDP 注入作为稳定产品承诺；
- Codex、dashi 参考和自动化能力不能反向改变知识优先顺序。
