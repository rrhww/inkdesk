# Inkdesk 产品愿景

## 当前定论

Inkdesk 的第一产品不是通用任务管理器，也不是只会回答问题的知识库，而是面向研发人员的知识看板：让项目资料、历史决策、代码上下文、证据和不确定性变成可阅读、可追溯、可复用的当前理解。

研发任务看板是第二阶段的执行工作面。它的任务来源既包括知识健康信号，也包括实时 PRD、Bug、重构、临时改造和执行过程中的新发现。知识驱动开发是差异化来源，但不是所有任务的前置条件。

```text
资料 / 决策 / 代码上下文
        -> 主题知识看板 -> 主题简报 / Context Pack
实时研发需求 ----------------------\
知识健康信号 -----------------------> 研发任务看板 -> 执行 / Review
执行过程发现 ----------------------/             -> 结果回写知识
```

## 一句话定义

Inkdesk 是一个 Knowledge Context Runtime：先把研发知识编译成带来源、带不确定性和可复核状态的主题上下文，再把实时需求和知识信号组织成可执行任务，逐步接入 Agent 执行与人工门禁。

## 要解决的痛点

研发人员反复遇到的不是“没有一个地方放文件”，而是：

- 不知道当前结论是否仍然有效；
- 找到文档，却无法判断依据、冲突和适用范围；
- 新需求开始时，历史决策和代码上下文需要重新拼装；
- 执行中发现的风险、测试失败和未解问题没有回到长期知识；
- 任务、知识和 Agent 对话彼此割裂。

Inkdesk 先解决“理解和复用上下文”的问题，再解决“推进研发任务”的问题。

## 第一产品形态：主题知识看板

知识看板不是把图谱换成几列卡片，而是围绕主题组织可行动的当前理解。每张主题卡至少回答：

- 当前理解是什么；
- 关键决策和相关代码在哪里；
- 结论来自哪些来源、能否回到原文；
- 哪些内容过期、缺证或互相冲突；
- 还有哪些未解问题和知识缺口；
- 最近何时被验证或使用。

图谱保留为关系探索视图，搜索和主题简报才是知识看板的主工作面。

## 任务与知识的关系

知识信号可以产生研发任务，但任务也可以直接来自实时需求或执行发现：

```text
知识信号：缺失证据 / 冲突 / 过期 / 未解问题 / 决策缺口
实时需求：PRD / Bug / 重构 / 临时改造
执行发现：新风险 / 测试失败 / 回归 / 后续优化
人工输入：用户直接提出的研发事项
```

任务创建不要求已有知识关联。创建后系统必须装配上下文：找到相关主题就生成 Context Pack；找不到就明确记录 Knowledge Gap。进入执行前，任务必须完成上下文检索，状态为 `ready` 或 `gap`，不能以“没有知识”为理由静默跳过。

任务和知识是双向、多对多关系：任务可以引用多个主题，一个主题也可以支撑多个任务；任务执行结果可以提出知识沉淀提案，但不能绕过审阅直接修改正式知识。

## 演进阶段

### K0：知识优先校正

统一产品叙事、领域模型和入口：`/app/wiki` 是当前主入口，图谱是辅助视图，任务看板和 Codex 宿主接入后置。

### K1：主题知识看板

完成主题列表、搜索、主题简报、来源追溯、关联文档/代码、更新时间和基础健康信号。先使用现有文件和派生索引，不提前恢复已删除的旧业务模块。

### K2：证据与知识健康

增加 Claim、Evidence、Conflict、Open Question、stale/unsupported/conflicting 状态和人工复核入口。健康状态表达“我们相信什么”，不使用任务状态列替代。

### K3：多来源研发需求与上下文装配

让实时需求、知识信号、执行发现和人工输入都能创建任务；自动搜索主题、决策、文档和代码，生成 Context Pack 或明确 Knowledge Gap。

### K4：dashi 式研发任务看板

在 K3 稳定后引入密集卡片、状态列、筛选、排序、详情、受控拖拽和 Review 门禁。任务卡必须展示来源、上下文状态、风险、下一步动作，并链接知识和证据。

### K5：Codex 执行与宿主接入

独立 Web 先完成闭环，再嵌入 Codex；接入会话、仓库、worktree、`codex exec --json`、事件、Review 和知识回写。CDP 只负责宿主适配，不持有业务真相。

## 成功标准

- 用户能围绕模块、业务概念和历史决策得到带来源的主题简报；
- 不确定、过期、冲突和缺证内容可定位、可复核；
- 实时需求可以立即进入任务 Backlog，知识信号和执行发现也能生成任务；
- 任务执行前有 Context Pack 或明确 Knowledge Gap；
- 任务、知识、证据、执行和结果可以互相追溯；
- Codex 或嵌入失败不会损坏独立 Web 和知识数据；
- 系统越用越能复用研发判断，而不是越用越像聊天记录或通用 issue tracker。

## 产品原则

- 知识内容先于任务形态，可信上下文先于自动执行；
- 主题卡是知识对象，任务卡是执行对象，两者不混淆；
- AI 可以提出结论和回写提案，但不能静默污染正式知识；
- 没有相关知识是合法状态，但必须记录为 Knowledge Gap；
- 图谱用于探索，摘要、来源和原文用于判断；
- 独立 Web 永远是稳定入口，Codex 只是后续宿主和执行器；
- 先做高频研发痛点，再扩展通用工作流和团队能力。
