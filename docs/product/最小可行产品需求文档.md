# Inkdesk MVP 产品需求文档

## 1. 产品背景

Inkdesk 当前是单人、本地优先、vault-first 的研发知识产品。现有系统已经具备 raw、ingest、wiki、ask、health 和关系图基础，但知识入口仍偏向文件浏览或图谱展示，无法稳定回答“当前理解是什么、依据是什么、哪里不确定”。

本阶段 MVP 不以 Dev Run 或 Codex 执行为中心，而是把现有内容升级成主题知识看板。研发任务看板、dashi 式交互和 Codex 宿主接入在知识内容可用后继续建设。

## 2. MVP 定位

MVP 的用户主路径是：

```text
进入 /app/wiki
  -> 浏览或搜索主题
  -> 阅读主题简报
  -> 追溯来源、决策和相关代码
  -> 查看缺证、过期、冲突和未解问题
  -> 必要时发起复核或沉淀提案
```

MVP 完成的标准不是“能画出图”，而是用户能围绕真实研发问题获得带来源、带不确定性说明、可继续追溯的主题简报。

## 3. 目标用户

主要用户是项目 owner 和需要频繁理解项目历史的研发人员。典型任务包括：

- 理解一个模块或业务概念；
- 查明某个技术决策为何形成；
- 判断某条结论是否仍有效；
- 为即将开始的研发需求准备上下文；
- 把新材料或执行结果沉淀为可审阅知识。

Claude Code、Codex、Cursor 等 Agent 是后续上下文消费者，不是当前 MVP 的产品主入口。

## 4. MVP 范围

### K1：主题知识看板

- `/app/wiki` 作为当前主入口；
- 主题卡展示当前理解、关键决策、关联文档/代码、来源数量、更新时间、未解问题和基础健康信号；
- 支持按模块、业务概念、历史决策和研发问题搜索；
- 主题详情提供 briefing、sources、related topics 和 graph 入口；
- 搜索优先返回主题简报，不只返回文件列表；
- 文件变更后派生索引和页面能够刷新；
- `/api/graph` 保留为兼容和辅助探索接口。

只读知识接口：

```text
GET /api/knowledge/topics
GET /api/knowledge/search?q=&scope=
GET /api/knowledge/topics/{id}/briefing
GET /api/knowledge/topics/{id}/sources
GET /api/knowledge/stream
```

主题简报至少返回：

- 主题摘要和当前理解；
- 关键文档与关键决策；
- 来源引用和更新时间；
- 相关代码路径和关联主题；
- 未解问题；
- 可信度或不确定性提示。

### K2：证据与知识健康

- Claim 与来源引用；
- stale、unsupported、conflicting 和 open question 信号；
- 从主题卡定位到具体问题内容；
- 健康状态筛选；
- 人工复核、补证或知识提案入口；
- AI 生成的变更在接受前不能改写正式知识。

健康状态表达知识可信度，不使用 `Todo/Doing/Done` 等任务状态。

## 5. 兼容与数据边界

- Vault Markdown 继续作为长期可恢复真相；
- 当前阶段优先使用文件系统和派生索引，不为主题看板提前恢复完整业务数据库；
- 现有 raw、ingest、wiki、ask、health 和 graph 数据继续可读；
- 不恢复已删除的 public、plans 或旧任务业务模块；
- 独立 Web 是验收环境，Codex iframe 不是 MVP 前置条件。

## 6. MVP 范围外

- dashi 式多列研发任务看板；
- 任务拖拽、负责人、工作树和执行会话；
- `codex exec --json`、自动认领和自动执行；
- 通用 issue tracker、行政或销售工作流；
- 多人协作、云同步和团队权限；
- AI 自动批准知识写入；
- 通用 Workflow 画布和高自治 Harness。

## 7. 后续任务模型边界

K3 开始后，任务可以由多种来源创建：

```text
originType:
  realtime_requirement
  knowledge_signal
  execution_finding
  manual

originRef:
  可选的知识信号、执行记录或外部需求引用
```

实时需求可立即进入 `Backlog`，不要求先关联知识。建卡后进行上下文装配：

```text
pending -> searching -> ready | gap | failed
```

- `ready`：已生成有关联知识的 Context Pack；
- `gap`：已完成检索，未找到足够知识，并记录 Knowledge Gap；
- `pending`、`searching`、`failed`：不能进入 `Ready` 或 `Doing`。

Context Pack 是执行门禁，不是建卡门禁。知识信号产生的任务必须回链到主题、Claim、证据和原文；实时需求与人工事项可以没有预存知识，但必须保存上下文检索结果。

## 8. 核心流程

### 浏览与搜索

1. 用户进入 `/app/wiki`；
2. 浏览主题卡或输入研发问题；
3. 系统返回匹配主题及简报，而不是只返回文件命中；
4. 用户进入主题详情查看决策、来源、代码和未解问题。

### 来源追溯

1. 用户从主题简报打开 Claim 或关键结论；
2. 系统显示来源定位、更新时间和支持状态；
3. 用户可跳回原文或关系图；
4. 无来源内容明确标记为不确定或 unsupported。

### 复核与沉淀

1. 用户从健康信号定位到具体问题；
2. 系统生成补证、冲突处理或更新提案；
3. 用户审阅后接受或拒绝；
4. 只有接受的变更才能进入正式知识。

## 9. 验收标准

### K1

- 使用真实 Wiki、PRD、ADR、设计文档和历史方案生成主题卡；
- 模块、业务概念、历史决策三类查询均能生成主题简报；
- 简报中的来源、更新时间和原文链接可以追溯；
- 无来源内容显式标记，不伪装为确定结论；
- 列表、详情、Markdown 阅读和关系图可以互相跳转；
- 文件变化后索引和页面能够刷新；
- Playwright 覆盖搜索、主题简报、来源追溯、空状态和失败状态。

### K2

- stale、unsupported、conflicting 和 open question 均有固定测试数据；
- 健康信号可以从卡片定位到具体内容；
- 复核动作不会静默修改正式知识；
- 现有 `/api/graph` 和知识浏览路径保持兼容。

## 10. 后续门禁

只有 K1-K2 的真实内容路径稳定后，才进入：

1. K3 多来源研发需求与上下文装配；
2. K4 dashi 式研发任务看板；
3. K5 Codex 会话、执行和宿主接入。

后续任务看板不能反向把知识看板降成任务附件库；任务状态变化也不能直接修改知识状态。
