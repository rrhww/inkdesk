# 产品定位与形态

## 产品定位

```text
Inkdesk 是面向研发人员的知识上下文与执行工作台。

当前先把 Wiki、PRD、ADR、设计文档和代码关系整理成主题知识看板，
让用户看见当前理解、来源、关键决策、未解问题和知识健康状态。

后续再把实时需求、知识信号和执行发现汇入研发任务看板，
为每个待执行任务装配 Context Pack，并逐步接入 Codex 等 Agent。
```

Inkdesk 不是：

- 只返回文件片段的普通 RAG；
- 以关系图替代内容阅读的图谱工具；
- 通用 issue tracker 或项目管理平台；
- 要求所有任务先从知识对象产生的知识治理系统；
- 自动改写正式知识或自动交付代码的黑盒。

Inkdesk 是：

- 研发主题、决策、证据和不确定性的可读投影；
- 为实时研发需求装配可信上下文的运行时；
- 让任务、知识、执行和沉淀形成双向追溯的工作台；
- 未来可嵌入 Codex、也始终可独立运行的本地产品。

## 产品形态

### 当前主界面

```text
/app/wiki        主题知识看板：主题卡、筛选、健康信号和最近变化
  /[id]          主题简报：当前理解、决策、来源、代码、问题和关系
/app/ask         知识搜索与 Context Ask
/app/raw         原始资料与来源
/app/ingest      知识提案审阅
/app/health      知识健康与复核入口
/app/graph       关系探索视图（辅助）
```

`/app/wiki` 是当前产品入口。图谱用于探索上下游关系，不能替代主题摘要、来源追溯和原文阅读。

### 后续任务工作面

K3 完成多来源建卡和上下文装配后，再将 `/app/runs` 演进为研发任务看板：

```text
Backlog -> Ready -> Doing -> Review -> Done
                       \-> Blocked
```

任务来源包括：

- `realtime_requirement`：PRD、Bug、重构、临时改造；
- `knowledge_signal`：缺证、冲突、过期、未解问题和决策缺口；
- `execution_finding`：风险、测试失败、回归和后续工作；
- `manual`：用户直接创建的研发事项。

建卡不要求选择知识主题。任务进入 `Ready` 或 `Doing` 前，必须完成上下文装配，形成 Context Pack 或明确 Knowledge Gap。

### Codex 与外部 Agent

独立 Web 是完整产品，Codex 是后续宿主和执行面：

```text
用户 <-> Inkdesk Web
           |-- 知识看板 / 任务看板 / Review
           |-- Context Pack / Knowledge Gap
           `-- Executor Adapter
                `-- Codex / Future Executors
```

CDP Host Adapter 只把稳定页面放进 Codex，不拥有知识或任务状态。Skill、CLI、MCP 和 Executor Adapter 必须调用同一应用服务。

## 核心闭环

### 当前知识闭环

```text
raw -> ingest -> topic / claim -> briefing -> health -> review -> topic
```

- `raw` 保存可追溯来源；
- `ingest` 管理候选认知变更；
- `topic / claim` 表达当前理解；
- `briefing` 为用户和任务提供可读上下文；
- `health` 暴露缺证、过期、冲突和未解问题；
- `review` 阻止 AI 静默修改正式知识。

### 后续研发闭环

```text
实时需求 / 知识信号 / 执行发现 / 人工输入
  -> 任务 Backlog
  -> Context Pack 或 Knowledge Gap
  -> 执行 / Review
  -> 交付结果与知识沉淀提案
```

知识不是任务的唯一来源，但知识上下文是执行前必须明确处理的条件。

## 产品层级

```text
Sources -> Topics / Claims -> Briefings / Health
        -> Context Assembly -> Tasks -> Execution / Review
        -> Evaluation / Harness -> Team Capabilities
```

前一层没有通过真实使用验收时，不以扩大功能面替代内容质量。

## 当前开发策略

```text
K0 产品与模型校正
  -> K1 主题知识看板
  -> K2 证据和知识健康
  -> K3 多来源任务与上下文装配
  -> K4 dashi 式研发任务看板
  -> K5 Codex 宿主和执行
```

dashi 的密集卡片、筛选、详情和全工作区宿主恢复机制是 K4-K5 的交互参考，不决定 K1-K2 的产品优先级。

## 第一批用户与价值

第一批用户是同时面对高频实时需求和大量项目历史的研发人员。他们需要：

- 快速理解模块、业务概念和历史决策；
- 判断结论是否可信、过期或存在冲突；
- 在新需求开始时复用相关知识；
- 在缺少知识时明确缺口，而不是让 Agent 猜测；
- 把执行结果沉淀回可复用上下文。

Inkdesk 的第一价值不是“替用户管理更多任务”，而是减少研发过程中的上下文重建和错误假设；任务看板在此基础上承接执行。
