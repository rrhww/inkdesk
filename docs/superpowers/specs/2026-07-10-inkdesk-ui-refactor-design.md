# Inkdesk Dev Run Console UI 重构设计

> 以 TraeWork Light 设计库重构 Inkdesk 的产品叙事、导航和核心工作流，并交付可验证的八视图静态 HTML 原型。

## 1. 目标与成功标准

Inkdesk 的首要产品形态是面向 AI 研发自动化的 Dev Run Console，而不是问答应用、Wiki 浏览器或知识治理后台。重构后的第一屏必须让用户立即理解三件事：当前有哪些研发任务、哪些阶段需要自己裁决、下一步如何推进。

本次设计服务于以下用户主路径：

```text
提交 PRD / bug / 改造目标
  -> 创建 Dev Run
  -> 查看阶段输出与执行事件
  -> 在关键门禁审批或退回
  -> 形成 Artifact / Deposit Proposal
  -> 更新 Wiki Claim
  -> 产生 Evaluation Signal
```

成功标准：

- 首页主叙事从 Ask 或知识指标转为 Dev Run 推进。
- 用户可以在两次点击内进入任一待确认阶段。
- Run 详情同时表达阶段、当前输出、执行事件、证据和下一步动作。
- Review 只承接必须由用户裁决的内容，不暴露后台 ingest 复杂度。
- Context Ask、Sources、Wiki、Skills 和 Evaluation 均能说明自己如何服务 Dev Run。
- UI 全面遵循 TraeWork Light token、组件和本地图标消费契约。
- 静态原型在 375、768、1024、1440 像素宽度下无横向溢出、文本遮挡或关键操作丢失。

## 2. 范围

### 2.1 本次交付

本次交付一套独立静态 HTML 原型，覆盖八个代表性视图：

1. Overview
2. Dev Run 详情
3. Review Queue
4. Context Ask
5. Sources
6. Wiki
7. Skills
8. Evaluation

Health 和 Settings 保留在正式导航中，但静态原型不为它们增加独立页面；它们的导航、状态和职责必须在壳层及相关视图中可辨认。原型用于确认信息架构、视觉语言和核心交互，不连接真实 API，也不伪造可被误解为线上结果的运行数据。

### 2.2 非目标

- 不修改服务端 API、状态模型或持久化协议。
- 不在本轮实现生产级 React 组件迁移。
- 不把后台 `raw / ingest / claim / lint / compile` 提升为用户主导航。
- 不扩展路线图之外的自动执行能力。
- 不设计深度配置、复杂报表或完整知识治理后台。
- 不覆盖现有 `web/preview-refactor.html` 或 `inkdesk-refactored-ui/`。

## 3. 产品架构与信息架构

### 3.1 用户可见模型

用户围绕一条 Dev Run 工作。每条 Run 由输入、阶段、阶段输出、门禁决策、交付物和沉淀结果组成。知识与评测是 Run 的支撑和结果，不与 Run 争夺主心智。

```text
Dev Run
  ├─ Context Pack
  ├─ 技术方案
  ├─ 技术评审
  ├─ Coding
  ├─ 测试 / 修复
  └─ Review / Deposit
       ├─ Artifact
       ├─ Wiki Claim
       └─ Evaluation Signal
```

`Compile` 表示后台执行活动，可出现在 Run 的事件流、阶段状态或技术详情中，但不作为一级导航。

### 3.2 左侧分组导航

```text
工作流
  总览
  Dev Runs
  审阅队列

上下文
  Context Ask
  Sources
  Wiki

自动化
  Skills
  Evaluations

系统
  Health
  Settings
```

导航规则：

- 桌面端使用固定左侧栏；组名作为弱层级标签，菜单项承担主要定位。
- 当前页面通过 `--bg-overlay-l2`、文字权重、图标和 `aria-current` 共同表达，不使用品牌填充，也不只依赖颜色。
- 侧栏顶部展示 Inkdesk 品牌和产品类别“R&D Automation”。
- 全局唯一持续可见的品牌 CTA 是“新建 Dev Run”。
- 移动端侧栏收进抽屉；顶部栏保留页面标题、菜单按钮和必要的上下文动作。

## 4. 页面设计

### 4.1 Overview

Overview 是行动队列，不是 KPI 仪表盘。内容优先级如下：

1. 待用户确认：显示需要审批、补充信息或处理冲突的阶段。
2. 进行中的 Dev Runs：显示任务名、任务类型、当前阶段、责任状态和最近活动。
3. 最近完成：提供交付物和沉淀结果的快速回看。
4. 系统摘要：仅在存在影响任务推进的异常时显示 Health 提示。

首页不使用大面积统计卡。必要数字以紧凑行内摘要呈现，例如“2 项待确认 · 3 条运行中”。空状态直接引导“新建 Dev Run”，不引导用户先提问。

### 4.2 Dev Run 详情

Run 详情是核心工作台，采用三段式结构：

- 顶部上下文：任务名称、任务类型、状态、发起时间、关联仓库和主要操作。
- 阶段轨道：Context、Solution、Review、Coding、Test、Deposit 六个稳定阶段，显示完成、当前、等待、阻塞状态。
- 工作区：当前阶段输出为主，右侧或下方显示证据、关联 Artifact 和阶段元数据。

Coding 阶段使用结构化工程事件流，不使用聊天气泡。事件包含时间、执行者、动作类型、目标、状态和可展开详情。典型事件包括读取上下文、修改文件、运行测试、门禁失败、重试和生成 Artifact。

阶段审批使用中性命令按钮，例如“批准进入 Coding”“要求修改”“查看证据”。品牌 CTA 只用于创建新 Run，不将所有推进动作染成品牌色。危险或不可逆操作使用明确的错误语义色并要求二次确认。

### 4.3 Review Queue

Review Queue 聚合跨 Run 的人工门禁。默认按紧迫度和阻塞时长排序，并允许按类型、Run 和风险过滤。

每个审阅项必须回答：

- 哪条 Run 被阻塞。
- 当前需要用户决定什么。
- AI 的建议和置信依据是什么。
- 影响范围和主要风险是什么。
- 批准、退回或保留后会发生什么。

审阅详情可包含方案差异、代码变更摘要、测试结果、Wiki patch 或冲突 claim。复杂后台字段默认折叠，用户先看到决策语义。

### 4.4 Context Ask

Context Ask 是面向当前研发任务的证据型查询工具。页面由问题输入、作用域选择、带引用回答和沉淀建议组成。

- 默认要求选择或继承一个 Dev Run；允许切换到全局知识范围。
- 回答正文与引用证据并列或紧邻展示。
- 明确标记证据充分度、知识缺口和冲突。
- 高价值回答可生成 Deposit Proposal，但不能直接写入正式 Wiki。
- 历史问答是辅助浏览，不采用聊天应用式的主视觉。

### 4.5 Sources

Sources 管理进入知识层的原始证据。列表重点展示来源名称、类型、关联 Run、处理状态、最近更新时间和健康提示。

导入操作作为页面级中性动作；来源状态使用语义标签。详情侧重可追溯性：原始位置、抽取结果、关联 claim、被哪些 Ask 或 Run 使用，以及是否存在解析失败或过期问题。

### 4.6 Wiki

Wiki 是“当前已确认理解”的可读投影。列表支持主题浏览、搜索和健康状态过滤；详情强调 claim、证据、最后验证时间、使用记录和 open questions。

页面不模仿笔记编辑器。默认是阅读和追溯界面；任何 AI 生成的认知变更均以 Proposal 进入 Review，不提供无门禁的直接覆盖。

### 4.7 Skills

Skills 展示可复用研发动作协议，而不是应用插件商城。每项 Skill 显示名称、类别、版本、状态、适用阶段、输入输出和最近验证情况。

用户可以检查 Skill 详情和关联 Evaluation。路线图尚未完成的调用、版本晋级或自动编排能力须显示“规划中”或“实验性”，不能用成熟产品状态包装。

### 4.8 Evaluation

Evaluation 展示 Golden Task、rubric、运行记录、版本比较和晋级门禁的理想信息结构。由于该能力处于路线图阶段，原型中的结果必须使用“示例数据”标识，页面级状态显示“规划中”。

Evaluation 不使用虚构增长图或成功率 KPI 营造完成感。核心是说明评测对象、测试集、判定规则、失败样例和与 Skill / Run 的关系。

### 4.9 Health 与 Settings 职责

Health 汇总知识新鲜度、冲突、来源解析、Skill 验证、Evaluation 和 Run 可靠性。默认后台运行，仅在影响任务推进时进入 Overview 或 Review Queue。

Settings 仅承接工作区、仓库、运行时、外部 Agent、MCP、通知和基础偏好，不承接日常业务操作。

## 5. 视觉系统

### 5.1 TraeWork 消费规则

- 仅使用 Light 模式。
- 直接消费 `colors_and_type.css` 的现有 token，不新增原始颜色或自定义色阶。
- 品牌色使用 TraeWork 原生紫色品牌 token，不覆盖为石墨靛蓝。
- 优先复用 `components.css` 中稳定的 `.ds-*` 原子，再用页面局部 CSS 完成布局。
- 图标仅使用 TraeWork `assets/icons/*.svg`；单色图标通过 `currentColor` mask 跟随组件语义色。
- 不使用远程字体、远程图片或其他关键远程资源。
- UI Kit 仅作为页面级证据，不直接复制为生产模板；组件 DOM 以 preview 和 component contract 为准。
- Dashboard 与 Skills Library 可作为组合参考；Dev Explorer 的 `componentUsageBasis` 为 `semantic-fallback` 且复用率低，只用于理解结构，不作为组件复用证据。

### 5.2 表面、边框与圆角

- 页面使用 `--bg-base-default`。
- 侧栏、次级区域和分组使用 `--bg-base-secondary` 或适用的 overlay token。
- 卡片只用于真正独立、可重复或可交互的对象；页面区段保持无框布局。
- 不使用 `paper-card`、装饰阴影、背景渐变、光斑或嵌套卡片。
- 普通页面容器和控件使用 `--radius-8`；`.ds-card`、`.ds-dialog`、`.ds-drawer` 和 `.ds-menu` 保留组件契约规定的 `--radius-12`；pill 仅用于状态和标签。
- 主要层级由排版、间距、分隔线和表面差异表达。
- 桌面页面内边距使用 `--spacer-32`，移动端使用 `--spacer-16`。相关容器间至少使用 `--spacer-16`，不同卡片组使用 `--spacer-24`，页面区段使用 `--spacer-32`，主要区域使用 `--spacer-48`。

### 5.3 排版

- 桌面正文基线为 14px / 20px。
- 页面标题按 TraeWork heading token 使用，紧凑面板不使用 hero 尺寸标题。
- 工程事件、路径、命令和标识符使用设计库提供的代码字体 token。
- 所有 letter-spacing 为 `0`，不使用 uppercase 加宽 eyebrow。
- 文本不可通过视口宽度连续缩放；采用稳定字号和响应式布局换行。
- 每个视图使用中文界面文案，保留 Dev Run、Context Ask、Skill、Evaluation、Artifact 等已成为产品概念的英文术语，不在同一控件内重复双语标签。

### 5.4 色彩与动作层级

- 每屏最多一个品牌 CTA，固定语义为“新建 Dev Run”。
- 阶段审批、筛选、导入、保存等使用中性按钮。
- 成功、警告、错误、信息状态只使用对应 status token。
- 状态同时使用文字或图标，不只用颜色区分。
- 链接与可点击文本保持清晰焦点态和足够对比度。
- 导航选中、Tabs、菜单项、分页和普通列表选中态使用中性 overlay 阶梯；品牌色只用于“新建 Dev Run”、品牌身份和少量有真实语义的强调。

## 6. 组件与交互约束

优先使用的 TraeWork 原子包括按钮、输入框、选择器、标签、Tabs、通知、对话框、菜单、空状态和面包屑。页面壳、阶段轨道、Run 行、审阅摘要、事件流和引用面板可由局部布局类组合，但不得重新实现已有原子的视觉属性。

图标默认使用 `--icon-size-16`，紧凑控件可用 `--icon-size-14`，较强的辅助锚点可用 `--icon-size-24`。不引入其他尺寸，所有图标在资源加载前保留固定宽高。

必须覆盖以下状态：

- 默认、hover、focus-visible、active、disabled。
- 加载、空、无搜索结果、部分失败、阻塞和权限不足。
- 长任务名、长路径、长引用标题和多行错误信息。
- Evaluation 的“示例数据 / 规划中”状态。

原型中的交互至少包括：

- 侧栏视图切换与移动端抽屉。
- Run 阶段切换和事件详情展开。
- Review 筛选与审阅项选择。
- Context Ask 作用域切换、引用展开和沉淀建议。
- Sources、Wiki、Skills、Evaluation 的列表与详情切换。
- 新建 Dev Run 对话框的打开、校验、取消和提交反馈。

交互动效遵循 TraeWork 时序：hover / focus 为 120ms，组件状态变化为 200ms，布局展开最多 300ms；仅使用透明度和不超过 4px 的位移。状态变化不得改变组件几何尺寸，`prefers-reduced-motion` 下移除非必要过渡和位移。

## 7. 响应式与可访问性

### 7.1 响应式

- `1440px`：固定侧栏，Run 详情允许主内容与证据栏双列。
- `1024px`：保留侧栏，减少次级列宽；必要时将证据区收进可切换面板。
- `768px`：侧栏转为抽屉，内容以单列为主，表格转为紧凑列表或允许容器内滚动。
- `375px`：顶部操作换行或收进菜单；阶段轨道可水平滚动但页面本身不得横向溢出；主操作保持可触达。

固定格式控件必须使用稳定尺寸或约束，包括图标按钮、状态标签、阶段节点、过滤器和计数器，避免内容变化造成布局跳动。

移动端所有交互命中区域至少为 44px；TraeWork 的 24–32px 紧凑控件通过外层命中区域扩展，不改变其视觉尺寸和桌面信息密度。

### 7.2 可访问性

- 使用语义化 landmark、标题层级、列表、表格和按钮元素。
- 所有交互可通过键盘完成，并有可见 `focus-visible` 状态。
- 图标按钮提供可访问名称和视觉 tooltip。
- 对话框管理焦点进入、循环和关闭后的焦点恢复。
- 表单错误与字段建立程序化关联。
- 动态状态变更使用适当的 live region，但避免重复播报事件流。
- 颜色对比、触控目标和 reduced-motion 行为达到常规产品界面要求。

## 8. 数据与内容原则

静态原型使用少量一致的示例数据表达真实产品关系。相同 Run、Skill、Source 和 Wiki claim 在不同视图中使用相同名称与状态，避免每页成为互不关联的演示。

示例内容遵循以下规则：

- 任务围绕 Inkdesk 自身研发场景，避免泛化占位文案。
- 不使用占位文案、未决标记或无意义编号。
- 未实现能力明确标记“规划中”“实验性”或“示例数据”。
- 错误和风险文案说明影响及下一步，不只显示“失败”。
- 页面不出现解释 UI 如何使用的宣传性说明；通过标签、状态和动作本身表达用途。

## 9. 原型技术边界

- 新建 `web/preview-dev-run-console/` 独立预览目录，与已有未跟踪原型隔离。
- 原型可通过普通 localhost 静态服务打开，不依赖 `file://` 安全绕过。
- 使用原生 HTML、CSS 和必要的轻量 JavaScript 完成视图与状态演示。
- 将 `colors_and_type.css`、`components.css` 和实际使用的图标按原目录结构复制到 `web/preview-dev-run-console/assets/traework/`。这些文件是设计库的只读快照，页面直接消费其中的 token、`.ds-*` 类和图标，不修改 TraeWork 设计库本体。
- 不引入与现有前端技术栈无关的大型框架或动画库。
- 任何动画只用于抽屉、对话框、展开收起和视图切换，并尊重 `prefers-reduced-motion`。

## 10. 验证与验收

静态原型完成后必须通过本地服务在真实浏览器中验证：

1. 八个视图均可通过导航到达，浏览器控制台无错误。
2. TraeWork CSS、组件和本地图标均成功加载，无远程关键资源失败。
3. 375、768、1024、1440 四个宽度均完成截图检查。
4. 页面无横向溢出、文本遮挡、不可读截断、嵌套卡片或失控圆角。
5. 键盘可访问导航、对话框、筛选、详情切换和主要动作。
6. 每屏品牌 CTA 数量不超过一个，阶段审批保持中性层级。
7. Evaluation 的路线图状态和示例数据标识清晰可见。
8. Overview 与 Run 详情能够独立讲清 Dev Run 主路径。
9. Review、Ask、Sources、Wiki、Skills 与 Evaluation 均能追溯到同一组示例对象。
10. 不覆盖现有用户文件，不改动 TraeWork 设计库本体。

## 11. 后续实施顺序

正式实现按以下顺序拆分：

1. 建立独立原型壳层、TraeWork 资源引用和共享页面数据。
2. 完成侧栏、顶部栏、响应式抽屉和新建 Run 对话框。
3. 完成 Overview 与 Dev Run 详情，先验证产品主叙事。
4. 完成 Review Queue 与 Context Ask，验证人工门禁和证据链。
5. 完成 Sources、Wiki、Skills 与 Evaluation。
6. 补齐所有状态、键盘交互和四档响应式表现。
7. 启动 localhost 服务，以真实浏览器完成截图、控制台、交互和溢出验收。

生产前端迁移须另行制定实施计划，将静态原型决策映射到现有 React 组件、路由、状态和 API；本 Spec 不授权直接替换生产页面。
